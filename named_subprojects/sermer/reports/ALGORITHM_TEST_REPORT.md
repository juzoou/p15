# Проверка C++-алгоритмов на tests — 26 октября 2026

Команда: `python scripts/benchmark_cpp.py`.
Данные полного прогона: [algorithm_results.csv](algorithm_results.csv).
Сгенерированные входы, решения и логи сохранены в `artifacts/algorithm_benchmark/` (не включаются в Git).

## Методика

Проверены все 15 режимов C++: 13 алгоритмов и переключатели `auto`, `divideconquer`.
Для каждого режима использованы 12 задач:

- DATA/COST из десяти допустимых файлов преподавателя `t01`–`t10`;
- `task5x4.txt` из `tests/5x4_test.zip`;
- `task89x98.txt` из `tests/89x98_test.zip`.

Перед запуском решения ORDER удалялся из производной копии: исходные файлы не менялись.
Таким образом, алгоритмы действительно строили новые решения, а не проверяли сохранённые ходы.
В частности, t10 в этом прогоне решается полностью; в оригинальном тесте его ORDER оставляет поле несобранным.

Лимит времени — 10 секунд на процесс. Лимит раскрытий — 200 000 для малых полей и 500 для поля 89×98.
Сниженный лимит большого поля ограничивает количество хранимых полных копий доски; отдельного лимита памяти нет.
У отжига этот параметр ограничивает итерации, на конструктивные методы он не действует.
Weighted A* использует стандартный вес 1.8.
Лимиты заданы для воспроизводимого ограниченного прогона, а не для доказательства отсутствия решения.

Каждый успешный результат независимо проигран Python-проверкой: проверены исходные размеры, поле и тарифы,
допустимость ORDER, достижение цели и совпадение числа ходов, стоимости и F с отчётом C++.

Для 5×4 лучший результат текущего прогона — Weighted A*: 74 хода, F=1826, собственное время решателя около 0.0094 с.
В исходном архиве есть ранее полученные решения в 62 хода: текущий результат не является лучшим известным для этой задачи.
Точные методы ограничены бюджетом, их оптимальность при успешном завершении этот прогон не опровергает.

Для 89×98 лучший результат прогона — columnbycolumn: 15 304 хода, F=856796, собственное время около 0.103 с.
rowbyrow дал 17 920 ходов, F=854180, около 0.148 с.
Автоматический выбор по форме поля выбрал rowbyrow и пропустил более короткое столбцовое решение.
Эти времена относятся к одному запуску на текущей машине и не являются устойчивой оценкой производительности.

## Выводы

На проверенных данных некорректных решений и сбоев нет. Для больших полей конструктивные методы дают результат
в небольшое время, но качество зависит от ориентации: имеет смысл сравнивать обе последовательности по стоимости.
Weighted A* на 5×4 дал значительно более короткий путь при текущем бюджете.
Для оценки точных методов на сложных задачах нужен отдельный прогон с увеличенными ресурсами.
Исходники алгоритмов во время этой проверки не изменялись.
